# 练习 02：追踪一次真实 Run

最后更新：2026-06-11

这个练习的目标不是“看前端能不能跑”，而是训练你把一次真实任务拆成后端链路、事件流、上下文、工具调用和最终交付。做完后，你应该能在面试里讲清楚：用户发一句话后，nanoCursor 内部到底发生了什么。

## 1. 准备工作

先启动后端和前端。

```bash
python -m uvicorn src.api.server:app --host 127.0.0.1 --port 8100
```

```bash
cd frontend
npm run dev
```

如果你启用了 Go sidecar，可以在启动脚本里选择开启，或者单独启动对应服务。练习本身不强依赖 Go sidecar，但你可以记录右侧栏里 Go 服务是否连接。

## 2. 任务 A：Lead 直接回答

在前端发送：

```text
哈喽
```

你需要记录：

| 观察点 | 应该看到什么 |
|---|---|
| conversation_id | 当前会话保持不变 |
| thread_id | 本轮 run 有自己的 thread_id |
| intent decision | 应该是简单问候或普通对话 |
| execution_route | 应该接近 `lead_direct_reply` |
| Agent 数量 | 只出现 Lead |
| 右侧进度 | 不应该出现完整代码交付任务 |
| Diff | 应该是 0 |
| 交付报告 | 不应该生成复杂交付报告 |

如果你发现问候触发了 Coder、Tester 或一整套开发任务，说明问题大概率在：

- intent router 判断过重。
- 前端复用了旧 run 的任务板。
- 会话和 run 的绑定关系没有清理。

## 3. 任务 B：只读项目分析

发送：

```text
帮我看看当前工作目录下面都有哪些重要文件
```

你需要记录：

| 观察点 | 应该看到什么 |
|---|---|
| 工具策略 | 只读为主 |
| 文件工具 | 可以读目录、读文件、查索引 |
| 写文件 | 不应该发生 |
| 子 Agent | 通常不需要，除非任务被判断成复杂分析 |
| 回复内容 | 应该是面向用户的总结，而不是原始工具日志 |

这类任务用来验证一个核心能力：系统能不能“看项目”，但不乱改项目。

## 4. 任务 C：真实代码交付

发送：

```text
帮我用 Python 写常见排序算法并比较性能，包含 README、源码、简单测试和性能对比脚本。
```

你需要记录：

| 观察点 | 应该看到什么 |
|---|---|
| execution plan | 有阶段、负责人、验收标准 |
| Agent 动态 | Lead / Coder / Tester 等按需出现 |
| 文件写入 | 新增源码、测试、README 或 benchmark |
| Diff | 新文件应该被统计 |
| 工具调用 | 文件写入、测试或命令执行有证据 |
| 失败恢复 | 如果测试失败，应该分类并尝试恢复 |
| 最终回复 | 应该总结改了什么、怎么验证、还有什么风险 |

如果任务结束后只有一句“我会帮你做”，但没有文件变化，说明执行层没有真正进入代码交付。你应该检查：

1. run 是否进入后台 workflow。
2. Agent Loop 是否提交了工具动作。
3. 工具策略是否错误拦截了 safe write。
4. 前端是否只展示了自然语言消息，漏掉了事件和 Diff。

## 5. 事件流检查

打开浏览器开发者工具或后端日志，观察事件类型。你至少应该能找到几类事件：

| 事件类型 | 说明 |
|---|---|
| run started | run 被创建 |
| intent / routing | 用户意图和执行路线 |
| plan / task | 执行阶段和任务板 |
| agent activity | Agent 正在做什么 |
| tool started / finished | 工具调用开始和结束 |
| file changed / diff | 文件变化 |
| approval wait | 高风险动作等待审批 |
| run completed / failed | 结束状态 |

不要只看 UI。UI 是事件流的投影，真正的可观测性在 EventStore 和后端状态里。

## 6. 上下文检查

对任务 C，重点检查上下文是否合理：

- 当前用户请求是否被保留。
- 当前计划和工具策略是否被保留。
- selected files 是否包含相关文件。
- omitted 是否记录被裁剪内容。
- token ledger 是否显示上下文压力。
- 如果触发压缩，压缩后是否保留关键锚点。

如果模型改错文件，优先怀疑上下文选择，而不是直接怀疑模型“笨”。

## 7. 复盘模板

每次跑完真实任务，按下面模板写复盘：

```text
任务：
工作区：
conversation_id：
thread_id：
intent route：
execution route：
创建的 Agent：
关键事件：
文件变更：
测试结果：
失败与恢复：
上下文是否命中：
最终用户回复是否干净：
我认为最需要改进的一点：
```

## 8. 自测问题

1. 为什么任务 A 不应该创建 Tester？
2. 为什么任务 B 不应该写文件？
3. 任务 C 里如果测试失败，系统应该先做什么？
4. 如何判断一个文件变更是由哪个 Agent 或哪个工具动作产生的？
5. 如果右侧任务板显示旧任务，应该检查会话、run、workspace 三者的哪层绑定？
6. 如果最终回复里混入大量工具日志，应该从 Agent 消息聚合还是前端渲染入手？
7. 如果上下文窗口接近 90%，系统应该如何处理？

## 9. 面试表达

你可以这样讲这个练习：

> 我没有只做一个聊天 UI，而是把一次代码任务拆成了可观测的 run。每轮请求都有 conversation、thread、intent、execution plan、Agent Loop state、EventStore 和工具证据。这样我可以区分简单问答、只读分析和真实代码交付，也能在前端展示 Agent 当前正在做什么。这个练习就是用三个任务验证这条链路是否真的成立。
