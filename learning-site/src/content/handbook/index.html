项目全景

nanoCursor 现在更适合被理解成一个“轻量 AI 编程工作台”，而不是普通聊天应用。 用户发起任务后，系统要判断意图、选择上下文、规划执行、调用工具、写文件、检查结果、 记录事件，并把过程展示给前端。

用户请求自然语言任务
Agent Loop判断与执行
Context Pack注入项目事实
Tool Runtime读写/命令/MCP
EventStore前端可感知运行

架构边界

Frontend 聊天、运行过程、任务进度、Diff、报告、设置 不要理解复杂业务状态来源 为什么 EventStore 能降低前后端耦合

我们做到目前为止，真正完成了什么

这部分是你复盘项目时最重要的主线。不要说“我做了很多功能”，要说“我逐步把一个玩具型 Agent 项目改造成有工程边界的本地编程工作台”。

阶段 1

从 LangGraph/早期实验转向自研 Runtime

你最早尝试的是多 Agent 工作流。后来发现重框架不一定更智能，于是转向更轻的 Agent Loop 和可控工具执行。

阶段 2

前后端分离和 EventStore

后端负责运行状态，前端通过 SSE/快照感知过程，避免用户不知道系统在干什么。

阶段 3

上下文、记忆和项目索引

不是把历史一股脑塞给模型，而是选择相关文件、摘要、偏好、技能和当前任务。

阶段 4

工具治理与 Runtime Hardening

把命令、Git、MCP、审批、权限、异步边界收拢，防止 Agent 无边界地改项目。

Agent Loop 怎么理解

成熟 AI 编程工具通常不是先画一个固定 DAG，而是围绕一个循环： 观察当前状态、判断下一步、调用工具、读取结果、修正计划、继续执行或停止。 你的项目现在也更应该围绕 Agent Loop 来讲。

核心理解

  • Agent Loop 不是“多 Agent 越多越好”，而是“该少的时候少，该分工的时候分工”。
  • 简单问答应该由 Lead 直接回答，不应该生成 Planner/Coder/Tester 全流程。
  • 复杂任务才需要创建临时子 Agent，比如 Coder、Reviewer、Tester、Action Agent。
  • 临时 Agent 应该绑定当前任务，任务结束后归档，而不是永久污染界面和状态。

src/api/services/agent_loop_controller_service.py运行控制
src/api/services/runtime_turn_service.py单轮运行状态

面试怎么讲 Agent Loop？

可以这样说：我没有用固定 DAG 强行编排所有任务，而是用 Lead Agent 做动态决策。 简单任务直接回复；小改动只创建 Coder；复杂任务才引入 Planner、Coder、Reviewer、Tester。 运行过程中每一步都会写入 EventStore，前端可以实时展示 Agent 正在做什么。

你要警惕一个面试坑：如果说“我做了多 Agent”，面试官很可能追问多 Agent 是否真的提升效果。 更稳的回答是：我关注的是任务复杂度驱动的 Agent 创建，而不是堆角色数量。

上下文管理与记忆机制

这是整个项目最值得讲的核心之一。Agent 能不能“聪明”，很大程度不是模型本身， 而是上下文给得对不对。

要解决的问题

  • 不能把完整历史、完整项目、所有文件都塞给模型。
  • 不能只靠模型自己猜项目结构。
  • 不能让旧会话、旧任务、旧 Agent 状态污染当前任务。
  • 用户偏好、Skills、最近变更、失败原因应该按需注入。

Context Pack 应该包含什么

内容 来源 作用
task_summary 用户当前请求 确定本轮任务目标
workspace_summary Project Index 让模型知道项目是什么
relevant_files 索引、最近变更、执行计划 减少盲目搜索和乱改文件
conversation_summary 会话摘要 保留长期上下文而不是完整历史
selected_memories 记忆选择器 注入用户偏好和项目事实
selected_skills Skill Registry 给模型工作方法，不直接授权工具

怎么学习这块？
  1. 先看 `ContextPack` 数据结构，不要先看复杂选择算法。
  2. 再看 `build_context_pack()`，理解每一类上下文从哪里来。
  3. 手动构造一个用户请求，想象哪些文件应该被选中。
  4. 最后看测试，理解哪些场景必须避免上下文污染。

工具治理与权限分级

Agent 项目真正脱离玩具感的关键，不是模型会不会说话，而是它能不能安全地调用工具。 你的项目里最值得讲的工程点之一就是工具治理。

权限分级

read_only

只读能力

读文件、搜索、项目索引、git status/diff。通常不需要审批。

safe_write

安全写入

写 workspace 内文件、局部编辑、生成报告。需要路径保护和快照。

risky_write / shell_risky

高风险操作

删除、移动、大规模替换、安装依赖、网络请求、git reset/push。必须审批。

为什么这重要

  • 用户信任来自“可控”，不是来自“自动化很猛”。
  • 工具调用必须有边界，否则 Agent 很容易误删、误改、乱装依赖。
  • 审批机制让高风险动作从“模型决定”变成“用户确认”。

关键代码定位

src/agent/strategy/tool_policy.py策略层工具权限
src/runtime/tool_policy_runtime.py运行时权限检查
src/api/services/action_execution_service.py工具执行入口
src/api/services/approval_service.py审批等待和确认
src/tools/path_safety.py路径越界保护
面试怎么讲工具治理？

可以说：我把工具能力按风险分级，读操作默认允许，workspace 内安全写入需要路径保护， 删除、安装依赖、git 高风险操作必须进入审批。这样 Agent 不是“想干什么就干什么”， 而是被 Runtime Policy 和用户审批共同约束。

Runtime 与异步边界

这是最近一轮重构的核心。简单说：以前很多地方可以直接 `subprocess.run`， 现在命令执行和 Git 执行都收敛到了统一边界。

为什么 FastAPI 里不能乱写阻塞调用

  • FastAPI 的 async route 运行在事件循环中。
  • 如果在 async route 里直接 `subprocess.run` 或同步网络请求，会阻塞事件循环。
  • 阻塞后 SSE、其他请求、取消任务和状态刷新都会变慢。
  • 解决方法不是“所有代码都 async”，而是把阻塞工作放进明确边界，用 `asyncio.to_thread()` 隔离。

当前边界

边界 同步 API 异步 API 负责什么
Command Runner run_command() run_command_async() shell 执行、超时、截断、Go fallback
Git Runner run_git() run_git_async() git status/diff/log/worktree 等短命令
Action Execution execute_action() execute_action_async() 工具调用统一入口
Go Runtime Client run_command_via_go_runtime() run_command_via_go_runtime_async() Python 调 Go sidecar

关键代码定位

面试表达重点：我没有盲目把所有代码改成 async，而是把真正会阻塞事件循环的命令和网络 I/O 收敛到少数 runtime boundary。

Go Sidecar 应该怎么理解

你不需要把整个后端改成 Go。更合理的路线是 Python + Go 混合架构： Python 负责 Agent 智能和业务状态，Go 负责 deterministic runtime work。

为什么 Go 适合做这些

  • 进程管理、超时、取消、stdout/stderr 流处理更稳定。
  • MCP stdio server 生命周期管理适合放在长期运行的 sidecar。
  • 文件监听和事件推送是 Go 的舒适区。
  • 可以作为执行边界，减少 Python 主事件循环压力。

为什么 Go 不应该做这些

  • 不应该做 Prompt Builder。
  • 不应该做记忆选择。
  • 不应该做 Agent Loop 决策。
  • 不应该接管 FastAPI 的业务模型。

下一步最值得做

优先级 1

Runtime Health

让 `/api/runtime/health` 清楚返回 Go 是否启用、是否可达、是否 fallback。

优先级 2

Runtime Event Bridge

把 Go 的 stdout/stderr/completed/failed 事件写入 Python EventStore。

优先级 3

Workspace Watcher

用 Go 监听文件变化，反哺 Project Index 和 ContextPack。

暂缓

全量 Go 重构

不建议。它会吞掉大量时间，还会削弱 Python Agent 系统的核心表达。

MCP / Skills 怎么理解

MCP 和 Skills 都是在扩展 Agent 能力，但它们不是同一种东西。 面试时你要能把这两者讲清楚。

能力 本质 风险 项目里的处理
MCP 外部工具/服务协议 工具权限、进程生命周期、输入输出安全 MCP tool call route 走 `execute_action_async()`
Skills 工作方法和领域知识 远程 Skill 内容可能有危险指令 静态导入、扫描风险、不直接授权工具

GitHub Skills 难点

  • 只能静态拉取文件，不能执行远程脚本。
  • 需要锁定 commit 和 checksum。
  • 导入前要扫描危险权限和敏感内容。
  • 前端 route 是 async，所以 GitHub 网络请求要有 async wrapper。

前端可感知运行

前端不是这个学习阶段的重点，但你要理解它为什么存在：Agent 做任务时，用户最怕的是“不知道系统卡住了还是在干活”。

前端应该展示什么

  • 当前 Lead Agent 正在判断什么。
  • 子 Agent 正在处理哪个文件或任务。
  • 工具调用是否等待审批。
  • 当前任务进度、Diff、风险、报告。
  • 失败阶段能否重试或恢复。

高频面试问答

1. 这个项目到底解决什么问题？

它探索的是本地 AI 编程工作台的后端架构：如何让 Agent 不只是聊天，而是能理解项目、 选择上下文、调用工具、修改文件、验证结果，并把运行过程可观察地展示给用户。

2. 为什么不用 LangGraph 了？

LangGraph 适合显式状态机，但 AI 编程任务更像动态 Agent Loop。固定 DAG 容易把简单任务复杂化， 也不一定提高智能程度。我保留了状态和阶段的可观察性，但把核心执行改成 Lead 动态判断。

3. 多 Agent 的意义是什么？

不是角色越多越好，而是按任务复杂度动态创建。简单问答 Lead 直接回答；代码小改动 Lead + Coder； 高风险或复杂任务才引入 Reviewer、Tester 或临时 Agent。

4. 上下文管理为什么重要？

模型聪不聪明很大程度取决于上下文。项目不能把所有历史和文件都塞给模型，所以我做了 ContextPack： 根据当前任务选择相关文件、最近变更、会话摘要、记忆、用户偏好和 Skills。

5. 为什么引入 Go？

不是为了替换 Python，而是把 deterministic runtime work 放到 Go sidecar： 命令执行、进程生命周期、MCP stdio 管理、运行事件、文件监听更适合 Go。 Python 仍然负责 Agent 推理、上下文和 API。

6. 你怎么解决 FastAPI 阻塞问题？

我没有把所有代码都硬改成 async，而是建立 runtime boundary。 shell 走 `command_runner`，git 走 `git_runner`，Action 走 `execute_action_async`， Go/GitHub 网络调用通过 async wrapper 隔离。

7. 工具调用怎么保证安全？

工具按风险分级，读操作、写操作、高风险 shell/git 操作分开处理。 高风险操作进入审批，路径写入有 workspace 边界保护，命令执行有危险命令拦截、超时和输出截断。

8. 这个项目还有哪些不足？

Go runtime 的健康状态、事件桥接、workspace watcher 还可以继续做实； 前端体验也还可以继续打磨。但当前后端已经有清楚的边界、测试和可讲的架构。

10 天吃透计划

真正的目标：你看到任何一个模块，都能说出“为什么要有它、如果没有会怎样、它的边界在哪里、它怎么被测试证明”。

最后的判断

如果继续让 AI 替你无脑堆代码，这个项目会变成负担。 如果你用它学习 Agent Runtime、上下文治理、工具安全、异步边界、Python + Go 分工， 它就是一个很好的个人项目。

你现在不缺代码量，缺的是“拥有感”。这份手册的目的就是帮你把代码量转化成理解力。
