# nanoCursor 学习资料包建设计划

> 目标不是再多写一份“看起来很完整”的文档，而是把 nanoCursor 这个项目变成一个可以被你真正吃透、可以复盘、可以面试讲清楚、以后也能继续维护的学习系统。

## 1. 建设背景

nanoCursor 已经不再是一个只有几段 demo 代码的小项目。它现在至少包含这些核心能力：

- 前后端分离的 AI 编程工作台
- FastAPI 后端事件流和运行状态持久化
- Agent Loop 与多 Agent 协作
- 上下文管理、项目索引、记忆机制
- 工具调用治理、权限分级、审批和恢复
- MCP / Skills 扩展能力
- Go sidecar 方向的工程化增强
- 前端可感知运行界面
- 测试、回归、真实任务验证

这些内容堆在一起以后，最大的问题不再是“代码够不够多”，而是：

- 你能不能解释每个模块为什么存在？
- 你能不能说清楚一次任务从前端发送到后端完成的完整链路？
- 你能不能回答“为什么不用 LangGraph / LangChain / 全 Go / 全 Python”？
- 你能不能讲清楚 Agent Loop、上下文、工具权限、异步执行之间的关系？
- 你能不能在面试里把它讲成一个工程系统，而不是“我让 AI 帮我写了很多代码”？

所以学习资料包的本质是给项目补一个“知识操作系统”：它要让你从会运行项目，走到能解释项目，再走到能独立修改项目。

## 2. 最终目标

学习资料包完成后，应该达到下面几个标准。

### 2.1 对你自己的标准

- 能用自己的话讲清楚项目定位、架构边界和核心取舍。
- 能沿着一次真实任务追踪完整执行链路。
- 能知道 Agent Loop、上下文管理、工具治理、MCP/Skills 各自解决什么问题。
- 能看懂主要后端模块，不再只依赖 AI 帮你改。
- 能知道下次要改某个功能时，应该先看哪些文件。
- 能把项目写进简历，并经得住面试追问。

### 2.2 对面试展示的标准

- 面试官问“你这个项目最核心的难点是什么”，你能回答到架构层。
- 面试官问“为什么这么设计”，你能回答到工程约束和替代方案。
- 面试官问“这个模块怎么实现”，你能说出核心类、核心接口、关键流程。
- 面试官问“还有什么问题”，你能诚实说出当前限制和后续改进。
- 面试官要求现场讲一次任务运行链路，你能按事件、Agent、上下文、工具、恢复顺序讲清楚。

### 2.3 对项目维护的标准

- 后续修改功能时，相关学习章节能同步更新。
- 每个核心模块都有代码地图和阅读路径。
- 每个章节都能指向真实代码，而不是只有抽象描述。
- 每个复杂概念都配一个真实任务案例。
- 学习资料不绑定某一次旧版本实现，避免很快过时。

## 3. 建设原则

### 3.1 先学习，后包装

这个资料包不是为了把项目包装得更高级，而是为了让你真的掌握它。文档里可以写项目亮点，但必须先解释清楚：

- 问题是什么
- 为什么需要这个模块
- 代码怎么组织
- 请求怎么流动
- 容易出什么 bug
- 面试会怎么追问

### 3.2 不再把所有内容塞进一个 HTML

单个 HTML 适合作为学习门户，不适合承载所有深度内容。最终结构应该是：

- `index.html`：学习门户、路线图、目录导航、关键图谱
- `chapters/*.md`：深度章节
- `exercises/*.md`：练习和复盘
- `interview/*.md`：面试问答和讲述模板
- `assets/*`：截图、流程图、架构图

HTML 负责“打开后知道从哪里学”，Markdown 负责“真正讲透”。

### 3.3 每章都必须绑定真实代码

不能只写“实现了 Agent Loop”。要写：

- 相关代码在哪些文件
- 入口函数是什么
- 数据结构是什么
- 事件如何发出
- 状态如何保存
- 错误如何处理
- 测试如何覆盖

### 3.4 每章都要能回答面试问题

每个技术章节最后都要附带：

- 5 个基础问题
- 5 个深入追问
- 2 个系统设计类追问
- 1 个“你这个方案有什么缺陷”的反问准备

### 3.5 不引入过重文档系统

现阶段不要上 Docusaurus、VitePress、复杂构建链。原因：

- 这个项目的主线不是文档站开发
- 过重工具会带来额外维护成本
- 当前最重要的是内容质量和学习闭环

最佳形态是轻量静态资料包：

- HTML 门户
- Markdown 深度章节
- 少量脚本做目录检查和链接检查

## 5. 内容层级设计

学习资料包应该分成四层。

### 5.1 第一层：项目全景

目标：让你在 30 分钟内知道这个项目是什么。

内容包括：

- 项目定位
- 为什么叫 nanoCursor
- 它和 Codex / Cursor / Claude Code / LangGraph 的区别
- 当前真实能力边界
- 当前还不成熟的地方
- 核心模块总览

对应文件：

- `index.html`
- `chapters/01-project-overview.md`
- `interview/01-project-pitch.md`

### 5.2 第二层：任务运行链路

目标：让你能追踪一次用户请求如何被处理。

内容包括：

- 用户从前端发送消息
- 前端如何创建/复用会话
- 后端如何判断任务类型
- Lead Agent 如何选择直接回答或进入 Agent Loop
- 如何创建临时 Agent
- 如何发送事件流
- 如何写文件、生成 diff、记录证据
- 如何形成最终回复

对应文件：

- `chapters/02-request-lifecycle.md`
- `maps/api-map.md`
- `maps/event-map.md`
- `exercises/01-read-the-request-lifecycle.md`

### 5.3 第三层：核心难点

目标：真正吃透项目最有含金量的部分。

核心章节：

- Agent Loop
- Agent 编排
- 上下文管理
- 记忆机制
- 工具治理
- Runtime 与异步边界
- EventStore 与 SSE

这些内容是简历和面试最值得讲的部分。

### 5.4 第四层：扩展能力与工程化

目标：理解项目如何从 demo 走向工程系统。

内容包括：

- MCP / Skills
- Go sidecar
- 前端可感知运行
- 测试与质量
- 启动部署
- 项目复盘

## 6. 每章统一模板

每个 `chapters/*.md` 都应该使用统一结构，避免写成散文。

```markdown
# 章节标题

## 1. 本章目标

读完这一章应该能回答什么问题。

## 2. 为什么需要这个模块

这个模块解决什么真实问题；如果没有它，系统会怎样。

## 3. 先验知识

需要先知道哪些 Python / FastAPI / SSE / Agent / LLM 概念。

## 4. 代码地图

列出相关文件、核心类、核心函数。

## 5. 核心数据结构

解释关键 schema、状态对象、事件对象。

## 6. 运行流程

按步骤解释一次真实执行。

## 7. 关键代码导读

选 3-5 段关键代码逐段解释。

## 8. 真实任务案例

用一个具体任务说明这个模块如何参与。

## 9. 常见 bug 和排查方式

列出历史上出现过的问题，以及怎么定位。

## 10. 设计取舍

为什么这样做；还有哪些替代方案；为什么没选。

## 11. 面试追问

给出问题和回答。

## 12. 自测题

读完后能不能不看答案回答。

## 13. 动手练习

给一个小任务，让你真正改一次代码或跑一次链路。
```

## 7. 章节详细规划

### 7.1 `01-project-overview.md`

目标：建立项目总认知。

必须讲清楚：

- nanoCursor 到底是什么
- 为什么它不是简单聊天机器人
- 为什么它也不是要替代 Codex / Cursor
- 项目当前最有价值的模块是什么
- 项目从比赛项目转向个人工程项目后，定位发生了什么变化

重点图示：

- 总体架构图
- 模块关系图
- 用户任务流图

面试重点：

- “你这个项目的核心价值是什么？”
- “为什么要自己做，而不是直接用 LangGraph？”
- “它和 Codex / Cursor 的差距在哪里？”

### 7.2 `02-request-lifecycle.md`

目标：把一次请求讲透。

必须覆盖：

- 前端发送消息
- 会话选择与创建
- 工作区绑定
- 后端 API 入口
- SSE 事件订阅
- Agent Loop 启动
- 事件持久化
- 前端实时显示
- 最终结果写回

必须包含一个完整案例：

```text
用户输入：帮我用 Python 写常见排序算法并比较性能
```

然后逐步追踪它如何经过系统。

### 7.3 `03-agent-loop.md`

目标：解释项目最核心的执行机制。

必须讲清楚：

- 为什么不继续走 DAG / LangGraph
- Agent Loop 的基本结构
- Loop 中每一轮发生什么
- 如何判断继续、完成、失败、需要工具、需要子 Agent
- 如何避免无限循环
- 如何和上下文、工具、事件流结合

重点回答：

- “Agent Loop 和 DAG 的区别是什么？”
- “为什么现代 AI 编程工具更像 loop，而不是固定流程图？”
- “你的 loop 如何做到可控？”

### 7.4 `04-agent-orchestration.md`

目标：讲清楚多 Agent 不是越多越好，而是按需创建。

必须覆盖：

- 默认只有 Lead Agent
- 简单问题直接回答
- 小代码任务创建 Coder
- 中等任务创建 Planner / Coder / Reviewer
- 高风险任务增加 Tester / Security / Migration
- 临时 Agent 生命周期
- 永久 Agent 和用户确认
- 子 Agent 并行/异步处理的边界

重点讨论：

- Agent 创建策略
- 子 Agent 结果合并
- Agent 状态如何在前端可感知
- 如何避免“问候语也创建一堆 Agent”

### 7.5 `05-context-management.md`

目标：讲清楚系统为什么“知道该看哪些文件”。

必须覆盖：

- 项目索引
- 入口文件识别
- 最近修改文件
- 文件摘要/outline
- 任务相关文件选择
- 用户偏好注入
- Skills 注入
- 上下文预算控制

重点回答：

- “为什么不能把整个项目都塞给模型？”
- “上下文选择错了会发生什么？”
- “如何评估上下文管理是否有效？”

### 7.6 `06-memory-system.md`

目标：区分记忆、上下文、历史记录。

必须覆盖：

- conversation_summary
- execution_summary
- user preference
- project facts
- tool evidence
- 长期记忆和短期记忆边界
- 什么时候写入记忆
- 什么时候不应该写入记忆
- 记忆如何过期或被覆盖

重点回答：

- “记忆机制是不是就是保存聊天记录？”
- “如何避免错误记忆污染后续任务？”
- “项目记忆和用户偏好有什么区别？”

### 7.7 `07-tool-governance.md`

目标：解释为什么工具权限是成熟 Agent 系统的基础。

必须覆盖：

- read_only
- safe_write
- risky_write
- shell_safe
- shell_risky
- approval
- 路径越界保护
- 文件备份
- 快照恢复
- 高风险操作二次确认
- 工具调用 evidence

重点回答：

- “为什么 Agent 不能直接拥有所有 shell 权限？”
- “如何设计工具权限分级？”
- “如何处理用户信任问题？”

### 7.8 `08-event-store-and-sse.md`

目标：讲清楚系统为什么能实时显示运行过程。

必须覆盖：

- SSE 和 WebSocket 的取舍
- 后端事件类型
- EventStore 持久化内容
- 前端如何订阅事件
- 历史会话如何恢复事件
- 事件顺序和幂等
- 断线重连策略

重点回答：

- “为什么不用轮询？”
- “SSE 有什么限制？”
- “事件流如何支撑可观测性？”

### 7.9 `09-runtime-and-async-boundary.md`

目标：解释异步正确性和阻塞边界。

必须覆盖：

- FastAPI async endpoint 的含义
- 哪些操作会阻塞事件循环
- 为什么需要 `asyncio.to_thread`

- 后台任务生命周期
- 取消、超时、清理
- 并发运行时如何保护状态

重点回答：

- “异步不正确会导致什么问题？”
- “怎么判断一个函数应该 async 还是 sync？”
- “为什么 Claude review 会说阻塞事件循环？”

### 7.10 `10-go-sidecar.md`

目标：理性解释 Go 引入的价值，而不是为了简历硬塞。

- “Python 和 Go 如何分工？”

### 7.11 `11-mcp-and-skills.md`

## 9. 练习设计

学习资料包必须有练习，否则容易停留在“看过”。

### 9.1 练习 1：读懂一次请求链路

要求：

### 9.4 练习 4：新增一个 Skill

### 9.5 练习 5：排查一次失败 run

要求：

- 制造一个工具失败
- 观察事件流

### 9.6 练习 6：设计新的 Agent 策略

- 写出伪代码

## 14. 每次写文档的工作流

每写一章都按这个流程：

1. 先列本章要回答的问题。
2. 用 `rg` 找相关代码。
3. 读入口文件和核心函数。
4. 画出流程。
5. 找一个真实任务案例。
6. 写章节正文。
7. 写面试追问。
8. 写动手练习。
9. 回头检查有没有空泛表述。
10. 更新 `index.html` 链接。

不要先凭印象写大段架构描述。每章都要从代码和真实运行出发。

## 15. 质量标准

### 15.1 内容标准

一章合格文档应该满足：

- 有明确学习目标
- 有代码地图
- 有真实流程
- 有设计取舍
- 有历史问题
- 有面试问答
- 有练习
- 不大量使用空泛形容词

不合格表现：

- 只有“实现了某某功能”
- 不指向代码
- 没有反例
- 没有局限性
- 全是 AI 味很重的总结

### 15.2 表达标准

文风要求：

- 像人在给自己写学习笔记
- 可以有判断和反思
- 少用“显著提升”“极大增强”这类空词
- 多写“为什么这样做”“这里容易错在哪里”
- 可以诚实写“当前实现还不完美”

### 15.3 可维护标准

- 每个文件开头写最后更新时间
- 涉及代码路径时使用相对仓库路径
- 代码重构后同步更新地图
- 过时内容不要留在主线文档里
- 旧文档可以归档，但不要混在学习主线里

## 16. 检查脚本规划

可以写一个轻量脚本：

`learning-site/src/content/handbook/scripts/check_learning_package.py`

检查内容：

- 必需目录是否存在
- 必需章节是否存在
- 每章是否包含固定标题
- `index.html` 是否链接到章节
- 是否存在空 Markdown 文件
- 是否存在明显 TODO

不要做复杂构建。这个脚本只是防止资料包烂尾。

## 17. 和现有文档的关系

项目里之前写过很多开发计划、复盘、路线文档。它们不应该全部塞进学习资料包。

处理原则：

- 当前仍准确的内容：吸收到新章节
- 已经过时但有复盘价值的内容：放入 retrospective
- 已完全无效的计划：归档或删除
- 不确定是否准确的内容：不要直接引用，先对照代码验证

学习资料包要成为新的主线文档，而不是旧文档的大杂烩。

## 18. 学习闭环

每个模块都按下面闭环学习：

```text
读章节 -> 看代码 -> 跑真实任务 -> 看事件/日志 -> 回答问题 -> 做小练习 -> 更新笔记
```

判断是否真正学会的标准：

- 不看文档能画出流程图
- 能指出相关代码文件
- 能解释一个历史 bug 的原因
- 能说出替代方案
- 能独立做一个小改动

## 19. 预计工作量

如果只是做一个“能用的学习包”：

- 目录骨架：0.5 天
- 核心五章：3-5 天
- 代码地图：1-2 天
- 面试包：1-2 天
- HTML 门户打磨：0.5-1 天

总计大约 6-10 个专注工作日。

如果做到“真正可以靠它吃透项目”：

- 需要 10-14 天
- 每天至少读一部分代码
- 每两天跑一次真实任务
- 每章都做练习

这比继续盲目堆功能更值得。因为现在项目最缺的不是代码体量，而是你对它的掌控感。
